## 2. 作業環境（エージェント）
役割ごとに Claude を分ける（D-004・D-013）。定義は `.claude/agents/` にある。

| エージェント | モデル | 役割 | 書いてよい場所 |
|---|---|---|---|
| 本人 | — | 決める・AI 系（ステップ 7）を作る（D-016） | AI 系（`app/llm/` など） |
| メイン（このセッション） | Opus 5.5 | 本人と壁打ちして決める・設計書とタスク票を書く・全体を回す | `docs/` |
| `implementer` | Sonnet | タスク票どおりに実装し、テストを書く | `app/`・`tests/`・`requirements.txt`・`README.md` |
| `reviewer` | Opus | 実装をレビューする（設計とのずれ・バグ・権限の漏れ） | 書かない（読むだけ・テストを走らせるだけ） |
| `framework-designer` | Opus | 話し合い系・技術コンサル系などのフレームワーク候補を出し、定義ファイルを書く | `app/frameworks/`・`docs/06_framework_design.md` のカタログ |

## 3. 1 ステップの進め方
```
① 本人と決める（未決事項を壁打ち）
② メインがタスク票を書く（docs/tasks/）
③ 本人がタスク票を読んで OK を出す      ← ここで止まる。OK なしに先へ進まない
④ implementer が実装・テスト
⑤ reviewer がレビュー → 指摘を implementer が直す（指摘がなくなるまで）
⑥ 本人が画面で動かして確かめる
⑦ 決定ログ・設計書を更新してコミット
```

## 4. 急に始めないための決まり（D-014）
- タスク票は、本人の OK が出るまで実装エージェントに渡さない。
- 実装エージェントは設計書を書き換えない。設計と合わない所に気づいたら、止めて報告する。
- 迷う所は止まらず、`open_questions.md` の「まとめて聞くこと」の仮の決定で進め、ステップの区切りでまとめて聞く（D-044）。
- タスク票に書いていないものは作らない。

## 5. 学びの決まり
- ステップを始める前に、そのステップで使う技術を挙げ、本人が知っているかを 1 つずつ確かめる。知らないものは先に短く学ぶ。
- 本人が自分で書いて学びたい箇所は、タスク票に書き、コードに `# TODO(自分で): …` として残す。

## 6. Git
- ステップごとにブランチを切る（例：`step/1-foundation`）。
- コミットの説明は日本語で書く。
- 本人の OK が出たものだけを既定のブランチに入れる。
