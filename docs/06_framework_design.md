## 1. 考え方：フレームワーク = 盤面の型 × 区画 × 進め方
フレームワークを 1 つずつ別の画面として作ると、増やすたびにプログラムが増える。そこで 3 つの部品に分け、組み合わせで表す。

| 部品 | 中身 | 例 |
|---|---|---|
| 盤面の型 | 付箋をどう置くか。プログラムはこの型の数だけ作る | ゾーン型・2 軸型・表型・ツリー型・タイムライン型 |
| 区画 | その型の中の具体的なマス | SWOT なら S・W・O・T の 4 マス |
| 進め方 | 時間の流れとルール | 個人ワーク → 公開 → まとめる → 投票 → 結論 |

SWOT・As-is/To-be・KPT・3C・PEST は、どれも「ゾーン型」の区画違いにすぎない。ゾーン型を 1 つ作れば、あとは定義ファイルを足すだけで増える。この定義の一覧が、後で AI が選ぶ「手札」になる。

### 1.1 盤面の型
| 型 | key | 説明 | 当てはまるフレームワーク | 作る時期 |
|---|---|---|---|---|
| ゾーン型 | `zone` | 決まったマスに付箋を置く | ブレスト（1 マス）・SWOT・As-is/To-be・KPT・3C・PEST・共感マップ・ビジネスモデルキャンバス | ステップ 2 |
| 2 軸型 | `axis` | 縦横の軸の上に自由に置く | ペイオフマトリクス・緊急度 × 重要度 | ステップ 4 |
| 表型 | `table` | 行 × 列のセルに値を入れる | 決定マトリクス（案 × 評価基準 × 重み） | 後で |
| ツリー型 | `tree` | 親子でつなぐ | ロジックツリー・なぜなぜ分析・マインドマップ | 後で |
| タイムライン型 | `timeline` | 時間軸に棒を置く | ガントチャート | 後で |

### 1.2 進め方（フェーズ）
どの盤面にも重ねられる共通の部品。決まりごとは [機能設計書 §5](02_functional_design.md) を見る。

| key | 名前 | 中身 |
|---|---|---|
| `individual` | 個人ワーク | 自分の付箋だけ見える。時間が来たら自動で公開（D-010） |
| `reveal` | 公開 | 全員の付箋が作成者名つきで見える |
| `cluster` | まとめる | 似た付箋を重ね、見出しをつける |
| `vote` | 投票 | 1 人 N 票で、付箋かまとまりに投票する |
| `conclusion` | 結論 | 班の結論を書く |

Think-Pair-Share や 6-3-5 のように「進め方そのもの」がフレームワークのものは、後でフェーズを足して表す。

## 2. 定義ファイルの仕様
置き場所：`app/frameworks/{key}.json`。1 ファイル = 1 フレームワーク。

| 項目 | 必須 | 説明 |
|---|---|---|
| `key` | ○ | 英小文字と `_`。ファイル名と同じ |
| `name` | ○ | 画面に出す名前 |
| `aliases` | ○ | 別名の並び。探すときに使う。例 `["ブレスト", "アイデア出し", "brainstorming"]` |
| `tags` | ○ | 探すときに使う短い言葉の並び。例 `["発想", "アイデア", "量を出す"]` |
| `yomi` | ○ | 漢字の名前・別名・タグの読み（ひらがな）。画面には出さず、探すときだけ使う。ひらがなで「ゆうせん」と打って「優先順位」に当てるため。例 `["ゆうせんじゅんい", "こうか"]` |
| `board_type` | ○ | `zone` / `axis`（ほかの型は作ってから使える） |
| `layout` | zone のとき | `{ "columns": 2, "rows": 2 }` |
| `zones` | zone のとき | 区画の並び。`key`・`label`・`hint` |
| `axes` | axis のとき | `x`・`y` それぞれ `label`・`low`・`high` |
| `quadrants` | axis のとき | 4 象限の `key`・`label`・`x`・`y`（`high` / `low`） |
| `phases` | ○ | 使うフェーズの並び。`individual` には `default_minutes`、`vote` には `votes_per_person` |
| `meta` | ○ | AI 推薦と一覧表示のための情報（§3） |

### 例：SWOT（ゾーン型）
```json
{
  "key": "swot",
  "name": "SWOT 分析",
  "aliases": ["スウォット", "SWOT分析", "強み弱み"],
  "tags": ["分析", "現状把握", "戦略", "内部環境", "外部環境"],
  "board_type": "zone",
  "layout": { "columns": 2, "rows": 2 },
  "zones": [
    { "key": "S", "label": "強み Strengths",     "hint": "内部・プラス" },
    { "key": "W", "label": "弱み Weaknesses",    "hint": "内部・マイナス" },
    { "key": "O", "label": "機会 Opportunities", "hint": "外部・プラス" },
    { "key": "T", "label": "脅威 Threats",       "hint": "外部・マイナス" }
  ],
  "phases": [
    { "key": "individual", "default_minutes": 7 },
    { "key": "reveal" },
    { "key": "cluster" },
    { "key": "vote", "votes_per_person": 3 },
    { "key": "conclusion" }
  ],
  "meta": {
    "purpose": "analyze",
    "thinking": "converge",
    "scenes": ["class", "business_plan"],
    "group_size": [3, 6],
    "minutes": [20, 40],
    "difficulty": 1,
    "good_for": ["自社・自分の現状把握", "戦略を立てる前の整理"],
    "pairs_with": ["brainstorm", "payoff_matrix"],
    "description": "内部の強み・弱みと、外部の機会・脅威を 4 象限で整理する",
    "source": "一般的な経営分析の手法"
  }
}
```

### 例：ペイオフマトリクス（2 軸型）
```json
{
  "key": "payoff_matrix",
  "name": "ペイオフマトリクス",
  "board_type": "axis",
  "axes": {
    "x": { "label": "実現しやすさ", "low": "難しい", "high": "易しい" },
    "y": { "label": "効果",         "low": "小さい", "high": "大きい" }
  },
  "quadrants": [
    { "key": "do_now", "label": "すぐやる",     "x": "high", "y": "high" },
    { "key": "plan",   "label": "計画してやる", "x": "low",  "y": "high" },
    { "key": "spare",  "label": "手が空いたら", "x": "high", "y": "low"  },
    { "key": "drop",   "label": "やらない",     "x": "low",  "y": "low"  }
  ],
  "phases": [
    { "key": "individual", "default_minutes": 5 },
    { "key": "reveal" },
    { "key": "vote", "votes_per_person": 3 },
    { "key": "conclusion" }
  ],
  "meta": { "...": "SWOT と同じ項目" }
}
```

## 3. メタ情報（AI 推薦のため）
最終ゴール（授業内容 → AI が 2〜3 個を選ぶ）のために、定義ごとに `meta` を持たせる。AI に渡すのは「この一覧」と「授業内容」だけ。AI は一覧にないものを作らず、選ぶだけ。

| 項目 | 意味 | 値 |
|---|---|---|
| `purpose` | 何のためか | `ideate` 発想 / `analyze` 分析 / `organize` 整理 / `decide` 決定 / `plan` 計画 / `reflect` 振り返り / `discuss` 話し合い |
| `thinking` | 考え方の向き | `diverge` 発散 / `converge` 収束 |
| `scenes` | 使われる場面 | `class` 授業一般 / `meeting` 話し合い・会議 / `business_plan` 事業計画 / `tech_consulting` 技術コンサル |
| `group_size` | 向いている人数 | `[最小, 最大]` |
| `minutes` | 目安の時間（分） | `[最短, 最長]` |
| `difficulty` | 難しさ | 1〜3 |
| `good_for` | 向いている授業・テーマの例 | 文章の配列 |
| `pairs_with` | 前後に使うと良いもの | `key` の配列 |
| `description` | 一文の説明 | 文章 |
| `source` | 出典・由来 | 文章 |

`pairs_with` があると、「2〜3 個を、使う順番つきで」提案できる（例：ブレスト → SWOT → ペイオフ）。

## 4. MVP の 3 本（D-007）
発想 → 分析 → 決定 を 1 本ずつ。作る盤面の型はゾーン型と 2 軸型の 2 つだけ。

| | ブレインストーミング | SWOT | ペイオフマトリクス |
|---|---|---|---|
| key | `brainstorm` | `swot` | `payoff_matrix` |
| 盤面の型 | ゾーン（1 マス） | ゾーン（2 × 2） | 2 軸（横：実現しやすさ / 縦：効果） |
| 区画 | テーマ 1 つ | S・W・O・T | すぐやる / 計画してやる / 手が空いたら / やらない |
| 進め方 | 個人ワーク → 公開 → まとめる → 投票 → 結論 | 個人ワーク → 公開 → まとめる → 投票 → 結論 | 個人ワーク → 公開 → 投票 → 結論 |
| 付箋の位置 | 区画の中で自由 | 区画の中で自由 | 軸の上の座標（0〜1）。象限は座標から決まる |
| 作る時期 | ステップ 2 | ステップ 2 | ステップ 4 |

## 6. フレームワークを増やす手順
フレームワーク作成エージェント（`.claude/agents/framework-designer.md`）を使う。

1. 本人が「どんな場面で使うものがほしいか」を言う（例：技術コンサルで、技術を選ぶとき）
2. エージェントが候補を 5〜10 個、カタログの行の形で出す（名前・盤面の型・目的・向いている場面）
3. 本人が残すものを選ぶ
4. エージェントが §2 の仕様どおりに定義ファイルを書く
5. レビューエージェントが、仕様に合っているか・`meta` が埋まっているかを確かめる
6. カタログの状態を更新する

**決まり**
- 今ある盤面の型で表せないものは、定義を書かない。「新しい盤面の型が必要」とカタログに書いて止める（型を作るのは開発のステップとして決める）。
- `meta` は全部埋める。AI 推薦の材料になるため。
- 他社の商標・図をそのまま写さない。由来は `meta.source` に書く。

## 7. 探す・おすすめ（D-021〜D-024。LLM なし）
先生は授業でフレームワークを選ぶ（D-021）。決まりごとは [機能設計書 §5「F-06」](02_functional_design.md)、画面は [画面設計書 §6](03_screen_design.md)。

| 仕組み | やり方 | 使うデータ |
|---|---|---|
| 打つと候補が出る | 文字を打つたびに絞り込む。手札が少ないうちは一覧を全部画面に送り、ブラウザで絞る | `name`・`aliases`・`tags`・`meta.description`・`meta.purpose` |
| 文字をそろえる | 全角/半角・大文字/小文字・ひらがな/カタカナの違いを無視する | — |
| よく使われている順 | 授業で選ばれた回数を数え、多い順に並べる。最初は全部 0 回なので、カタログの順 | `CourseFramework` の行の数 |
| 進め方を抜く | 選んだあと、まとめる・投票・結論を外せる。個人ワークと公開は外せない（D-023） | 定義の `phases` |

今回は入れないもの（記録が貯まってから。AI 系は本人が作る。D-016・Q16）：
- 「一緒によく使われている」（協調フィルタリング）
- 「授業のテーマに合うもの」（キーワードの一致・LLM）

勉強用のメモ：[探す・おすすめ](learning/04_search_recommend.md)

## 8. 似た意見をまとめる
- **今（LLM なし）**：付箋を別の付箋の上に落とすとまとまりになる。見出しは手で書く。
- **後で（LLM）**：公開のときに「似ている候補」を出し、人が承認する。見出し・要約も提案する。モデルはステップ 7 で決める。
- まとまりは最初から `Cluster` テーブルで持つので、LLM を足すときに作り直さない。

## 9. 可視化のために記録すること
すべての操作を `Event` に追記する（[データ設計書 §3](04_data_design.md)）。今は教員向け（D-008）なので「フレームワークの中でどう考えたか」が中心。学生が自由に選ぶ形を足したときのために、選んだ人（`chosen_by`）も最初から残す。

| 記録 | 分かること |
|---|---|
| `board.created` | どのフレームワークを、誰が、何番目に選んだか |
| `phase.changed` | 各フェーズにかけた時間 |
| `note.created` / `note.moved` / `note.edited` | 誰がどれだけ書いたか（発言の偏り）、どの区画が厚いか |
| `cluster.created` | どうまとめたか |
| `vote.cast` | 何が選ばれたか |
