> 状態: 壁打ち中　最終更新: 2026-11-05

## 1. 一言でいうと
グループワークで、班のみんながフレームワーク（ブレスト・SWOT・ペイオフマトリクス など）の上に付箋で考えを書き込み、まとめていく場所。教員はそれを上から見られる。画面は Teams のイメージ。

## 2. 目的
1. **考えをまとめる場所をつくる** — 招待コードで集まった班が、同じボードに同時に書き込める。付箋には誰が書いたかが残る。
2. **同調を防ぐ** — 意見を先に見せると考えが固まってしまう。だから最初は、他の人の付箋が見えない状態で各自が書く。
3. **フレームワークの中での考え方を可視化する（最初は教員向けの教育支援）** — 教員がフレームワークを指定し、学生がその中でどう考え・どうまとめ・何を選んだかを教員が見る。学生が自由にフレームワークを選ぶ形は後で足し、そのときは「選び方」も記録する（D-008）。
4. **（最終ゴール）AI が授業に合うフレームワークを選ぶ** — 教員が授業内容を入れると、AI が用意済みのフレームワークの中から 2〜3 個を提案する。0 から作らせず、手札から選ばせる。だから先にフレームワークを揃えることが土台になる。

## 3. 利用者とロール
| できること | 教員 | 学生 |
|---|---|---|
| 授業をつくる・招待コードを発行する | ○ | × |
| コードで授業に参加する | — | ○ |
| 班を分ける | ○ | × |
| 授業で使うフレームワークを指定する | ○ | ×（後で自由に選べる形も足す。D-008） |
| 個人ワークの時間を決める・早めに公開する | ○ | × |
| 自分の班のボードに書く | ×（見るだけ。D-011） | ○ |
| 個人ワーク中の付箋を見る | ○（全員分。D-011） | 自分の分だけ |
| 他の班のボードを見る | ○（全班） | ×（案。Q6） |
| ダッシュボード（可視化）を見る | ○ | × |

**一方通行**: 教員からは学生の中身が見える。学生からは教員の画面にも他班の中身にも入れない。画面で隠すだけにせず、サーバーが毎回ロールを確かめ、見せてはいけないデータはそもそも送らない。

## 4. 授業の流れ（中心の体験）
**教員**
1. 授業をつくる → 招待コード（例 `K7Q2MX`）が出る
2. 学生が集まったら班に分ける（手動 / ランダム）
3. この授業で使うフレームワークを指定する（例: ブレスト）
4. 個人ワークの時間を決めてスタート → 時間が来たら自動で公開（早めに公開もできる。D-010）
5. 各班のボードを見守る（個人ワーク中も全員分見える）
6. ダッシュボードで、各班がフレームワークの中でどう考えたかを見る

**学生**
1. 初回は「招待コード + 名前 + パスワード」で登録して授業に入る。次からは「名前 + パスワード」でログイン（D-009）
2. **個人ワーク**: 他の人の付箋が見えない状態で、自分の考えを付箋に書く。残り時間が表示される
3. **公開**: 時間が来ると全員の付箋が見える（作成者名つき）
4. **まとめる**: 似た意見を同じ所に重ね、一言の見出しをつける（最初は手で。後で LLM）
5. **アウトプット**: 班としての結論を残す

## 5. 設計の柱
- **P1 個人で考える時間を守る** — 個人ワーク中、サーバーは他の学生の付箋を送らない。時間が来たらサーバーが公開に切り替える。
- **P2 誰が書いたかが残る** — 付箋の作成・移動・まとめ、すべてに「誰が・いつ」を持たせる。これがそのまま可視化の材料になる。
- **P3 フレームワークは「定義データ」で持つ** — 1 つずつ画面をプログラムせず、「盤面の型 + 区画 + 進め方」を書いた定義ファイルで増やす。AI が後で選ぶ「手札」は、この定義の一覧そのもの。→ [フレームワーク設計](02_frameworks.md)

## 6. 画面構成（Teams のイメージ）
```
+--------+------------------+------------------------------------------+
| 授業    | 経営戦略論 #3     | タブ: [ブレスト] [SWOT] [ペイオフ]          |
| 一覧    |                  | 個人ワーク中 残り 4:32（0:00 で自動公開）     |
|        |  * 1班           |   +----------------+----------------+    |
| (Teams |    2班           |   | 強み S          | 弱み W          |    |
|  の     |    3班           |   | [付箋: 山田]    |                |    |
|  チーム)|  --------------  |   +----------------+----------------+    |
|        |  教員のみ:        |   | 機会 O          | 脅威 T          |    |
|        |   ダッシュボード   |   +----------------+----------------+    |
+--------+------------------+------------------------------------------+
```
- 左端のレール: 参加している授業（Teams の「チーム」に当たる）
- 2 列目: 班の一覧（Teams の「チャネル」）。学生には自分の班だけ出る
- メイン: その班のボードがタブで並ぶ。タブ 1 つ = フレームワーク 1 つ
- 教員にだけ: 全班一覧・ダッシュボード

## 7. 技術構成（案）
| 層 | 案 | 選ぶ理由 | 後で変えるとき |
|---|---|---|---|
| Web サーバー | FastAPI + Uvicorn | Python。WebSocket が標準で使える。API の説明ページ（/docs）が自動で出る | — |
| リアルタイム同期 | WebSocket | 付箋の追加・移動を班全員の画面へすぐ届ける | サーバーを複数台にしたら Redis Pub/Sub |
| DB | SQLite + SQLAlchemy 2.0 | ローカルでファイル 1 つ。インストール不要 | 接続先 URL を変えて PostgreSQL へ。類似検索は pgvector |
| テーブル変更の管理 | 最初は自動作成、形が固まったら Alembic | 初期は変更が多いので軽くする | — |
| 画面 | Jinja2 テンプレート + 素の JavaScript（ES Modules）+ CSS | ビルド不要で `python` だけで起動できる | 画面が複雑になりすぎたら React など |
| ログイン | セッション Cookie + パスワードのハッシュ化（argon2） | ローカル運用には十分 | 学校の SSO |
| 教員アカウントの作成 | コマンドで作る（`python -m app.cli create-teacher`） | 画面から誰でも教員になれる穴を作らない | 管理画面 |
| テスト | pytest + httpx | FastAPI の定番 | — |
| LLM | **未決**（呼び出し口だけ 1 か所に作っておく） | 本人指定：後で決める（D-003） | M7 で決める |

## 8. データの持ち方（案）
| テーブル | 中身 |
|---|---|
| User | 名前（ログイン名・全体で重複不可）、ロール（teacher / student）、パスワードのハッシュ |
| Course（授業） | 名前、担当教員、招待コード |
| Enrollment | 授業 × ユーザー（誰がどの授業に参加しているか） |
| Team（班） | 授業、名前 |
| TeamMember | 班 × ユーザー |
| Board（ボード） | 班、`framework_key`（どの定義から作ったか）、`chosen_by`（教員 / 学生。今は教員だけ）、今のフェーズ、フェーズの終了予定時刻 |
| Note（付箋） | ボード、区画、作成者、本文、位置、所属まとまり、作成・更新・削除日時 |
| Cluster（まとまり） | ボード、見出し、要約、作った人（人 / AI） |
| Vote（投票） | 付箋かまとまり × ユーザー |
| Event（記録） | いつ・誰が・どの班/ボードで・何をしたか（JSON）。消さずに足していく。可視化と AI の材料 |

フレームワークの定義はリポジトリ内の JSON ファイル（`app/frameworks/*.json`）で持ち、Git で管理する。教員が自作する機能を付けるときに DB へ移す。

## 9. 開発の進め方
| 役割 | 担当 | やること |
|---|---|---|
| 決める | 本人 | 未決事項を壁打ちで決める |
| 設計・レビュー | Opus 5.5（このセッション） | 設計書・決定ログ・タスク票を書く。Sonnet のコードをレビューする |
| 実装 | Sonnet（サブエージェント） | 設計書とタスク票どおりに実装し、テストを書く |
| レビュー | Opus（別のサブエージェント） | 設計とのずれ・バグ・権限の漏れを確認 → 指摘を Sonnet が直す |

1 タスクの流れ: 設計書に節を書く → タスク票（`docs/tasks/`）→ Sonnet が実装 → Opus がレビュー → 修正 → 本人が画面で確認。
本人が自分で書いて学びたい箇所は、`# TODO(自分で): …` として残して渡す。
